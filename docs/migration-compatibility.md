# 数据库发布兼容性

迁移任务运行时旧应用仍在提供服务。应用发布失败只恢复旧镜像，不回滚数据库。
每次涉及 schema 的发布都要明确允许回滚到哪个版本，并验证那个版本仍能使用迁移后的数据库。

## 变更顺序

1. 扩展：新增表或兼容字段；旧应用未提供的新字段应允许空值或具有适当默认值。
2. 过渡：新代码迁移读写方式，完成数据回填，观察后再停止旧字段写入。
3. 收缩：旧版本已不在运行且退出回滚范围，才删除旧字段、收紧约束或移除兼容路径。

禁止修改已经发布的迁移来修正线上结构，使用新的增量迁移。`down` 可执行不代表数据可无损恢复。

## 验证与发布记录

在临时数据库上先运行上一可回滚版本的迁移并写入代表性数据，再运行本次迁移。
分别用旧应用和新应用检查关键查询与写入，至少覆盖本次变更涉及的模块。
确认旧应用省略新增字段时仍能写入，旧数据能被新代码读取，外键、唯一约束和默认值未破坏现有操作。
新应用写入数据后还应再次验证旧应用读取，覆盖应用回滚路径。

PR 应记录：迁移版本、允许回滚的应用版本、兼容性理由、旧新版本验证命令与结果、收缩阶段的回滚限制。
仓库 CI 检查已合入迁移不可改写、Ent 字段/索引一致性和 up/down/up；这些检查不代替旧应用行为验证。
发布前保留数据库备份或恢复点；自动部署只回滚应用，数据库恢复由明确的恢复方案执行。

## 00003：账号角色管理

新增 `user_audience`、`account_role_state`、`account_role_audit`，原有账号、身份、会话和角色绑定表不变。
迁移从现有绑定及会话回填 audience 标记；已有 admin 会关闭该 audience 的一次性初始化入口。
新增三条权限码使用既有种子 admin 的 `system:*` 策略，无需修改旧角色策略。

发布顺序：备份 → 执行两个方言中所选的 00003 → 替换所有旧副本 → 启用管理员初始化和角色管理。
滚动发布期间不要使用新的角色管理接口。旧代码无法理解“主动清空角色”，可能在再次登录时恢复 `user`；
因此**一旦使用角色管理，允许回滚的应用必须包含本次 `user_audience` 语义**，不能自动回滚到 `298c783`
或更早版本。首次部署后使用功能前，应先把当前版本作为已验证的回滚基线。

回滚应用时保留数据库版本 3；`down` 仅供隔离测试或停服恢复，执行前导出新增审计和角色配置。
两方言的迁移往返、Ent 对齐和账号/会话用例由 `make test`、`make test-mysql` 验证。
