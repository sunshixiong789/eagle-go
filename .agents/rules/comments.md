# 注释规范

在新增或修改手写 Go、Proto 或整理既有注释时读取。接口契约必须注释，普通方法按复杂度补充。

## Go 接口

- 具名 `interface` 类型及其每个方法必须有注释，包括包内私有接口；匿名接口的方法也要说明调用约定。
- 类型说明职责，方法说明业务行为；存在特殊约定时，补充空值或未找到语义、关键领域错误、原子性、幂等性、并发或资源所有权等调用方需要遵守的契约。
- 契约集中维护在接口定义处，实现方法仅补充实现特有的约束或原因，不复制整段接口注释。

## REST API

- `api/**/*.proto` 的每个 `service` 和 `rpc` 必须说明业务用途与行为；存在全量覆盖、级联删除、幂等、并发版本检查或其他副作用时必须写明。
- 字段存在不明显的枚举含义、单位、默认值、缺省语义或不可变约束时必须说明，尤其区分“未传”“传零值”“传空集合”。
- 手写 REST handler 必须有简短的用途注释；完整 API 契约维护在 Proto。手写的健康检查等 HTTP 入口也应在注册处或处理函数上说明用途与成功条件。
- HTTP 路由、`access`、`perm` 和校验约束以 Proto 声明为准，注释补充业务语义，不机械抄写配置。生成代码和 OpenAPI 通过 `make api` 更新，禁止手改生成文件。

## 普通函数和方法

- 涉及业务不变量、状态转换、事务边界、并发、幂等、补偿或不明显的设计取舍时必须解释；优先说明原因、边界和失败语义。
- 简单取值、直接转发和显而易见的转换不强制添加注释；已有接口契约或局部注释足以解释的，不重复添加方法长注释。

## 写法与维护

- 优先使用中文，Go 声明注释以被注释的标识符开头；简单契约一句话即可，不添加仅复述名称的空泛注释、占位 TODO 或无意义的参数返回值模板。
- 注释必须与当前实现一致，不把预期行为写成已实现的保证；涉及一致性或失败恢复时，明确保证的范围。
- 行为变更时同步更新相关注释；修改既有接口时补齐本次涉及的契约，除非任务明确要求，不顺手全仓补注释。
